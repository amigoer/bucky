# ADR-002：R2 首版与按类型扩展存储

- 状态：已采纳；v0.1 只接 R2 与类型接入顺序由 [ADR-005](0005-four-storage-types-first-release.md) 替代
- 日期：2026-10-18
- 相关：[ADR-001](0001-tech-stack.md)、[开发架构](../architecture.md)、[开发规划](../development-plan.md)

## 背景

最初 SPEC 将多个云厂商、通用 S3 预设和原生增强功能一起纳入首版，且要求所有基础读写都走 S3 兼容层。这会把厂商权限、签名与 API 差异集中带入第一个版本，并让 OSS 的原生接入受 S3 能力边界限制。

Amigoer 明确要求架构简单，第一版先接 Cloudflare R2，之后按存储类型规划 AWS S3、阿里云 OSS 等服务。

## 决策

### 一个本地核心，四层结构

保持 Go + Wails v3 + React，采用入口适配、应用服务、核心契约、存储适配四层。GUI、CLI、MCP 共用 `service`；SDK 调用集中在 `drivers`。本地 SQLite 和系统钥匙串分别保存状态与凭证，不建设远程业务服务、运行时插件或通用工作流引擎。

### v0.1 只有 R2

只有 `r2` 类型可以创建连接。保留原有的可靠传输、计划确认、预览/分享、图床/用量和 Agent 目标，拆成 Phase 0–6 逐步验收；不再把接完全部厂商作为首版发布条件。

MinIO 和 RustFS 继续作为 S3 协议测试后端，不出现在首版支持列表。R2 的签名、权限、校验、CORS 和链接行为必须用真实服务验证。

### 业务类型与协议实现分开

| 类型 | 适配策略 |
| --- | --- |
| R2 | 以 AWS SDK for Go v2 调用 R2 的 S3 API，集中配置 endpoint、region 和兼容策略 |
| AWS S3 | 后续复用同一个 S3 协议实现，增加 AWS 配置、凭证来源及能力验证 |
| 阿里云 OSS | 后续用 OSS Go SDK v2 实现相同业务契约，基础读写也使用原生适配器 |
| 通用 S3 兼容服务 | 在独立版本开放自定义 endpoint 和已验证预设，不把协议兼容当作全面支持 |
| 其他原生云服务 | 按类型逐一接入；仅在相应版本添加 SDK、目录和界面 |

顺序为 v0.1 R2 → v0.2 AWS S3 → v0.3 OSS → v0.4 通用 S3 兼容服务 → v0.5 COS/Kodo → 后续非 S3 类型。跨云同步等功能不再占用原先的 v0.2 编号，其顺序以开发规划为准。

### 小接口与显式注册

基础契约只覆盖实际使用的对象读写。桶发现、预签名、分片、服务端复制和厂商增强使用独立可选接口；能力声明与实现保持一致。只读限制与操作确认在应用服务统一执行，不分散到入口或厂商代码。

使用普通 Go 工厂注册类型。R2 和 S3 共用协议代码；不为每个厂商复制业务用例，也不为了将来的文件系统/迁移功能先设计大而全接口。

### R2 配置遵循真实权限和域名边界

支持指定桶名连接，不把 `ListBuckets` 权限设为使用前提。R2 的 S3 凭证不与 Cloudflare 管理 API token 混用：OAuth 登录（[ADR-003](0003-cloudflare-oauth-connection.md)）只是用管理 API 铸出一把单桶 R2 令牌，随后仍以派生的 S3 凭证访问对象。预签名链接使用 R2 S3 域名，自定义公开域名独立配置。具体限制见开发架构及官方资料。

## 对已有决策的影响

- ADR-001 的 Wails、React、Go、Taskfile、钥匙串、SQLite、分片状态持久化及双本地测试后端继续有效。
- 替代“首版多厂商预设”“全部厂商基础读写强制 S3”“国内云 Phase 6 接入”“v0.2 直接做跨云同步”等范围假设。
- ADR-001 的未来厂商 SDK 列表只是接入时的参考，不是 Phase 0 安装清单；到各类型实施时重新核实并锁定版本。
- 本 ADR 记录驱动边界和接入顺序；具体接口随 Phase 1 的实际用例细化，不另行预留冲突的 ADR 编号。

## 备选方案

- **首版接入全部厂商**：并行处理过多兼容和权限差异，R2 的完整体验更晚才能验证。
- **所有云都强制走 S3**：复用较多，但原生服务会受兼容层限制，无法自然表达其能力与错误。
- **每个厂商独立实现全部流程**：短期局部简单，但传输、确认和数据恢复容易出现多套行为。
- **预建插件和工作流平台**：当前没有运行时插件需求，增加工程负担，不能减少首个 R2 版本的工作。

## 后果

- 首版范围清楚，可在真实 R2 上验证完整流程；AWS S3 与 OSS 作为独立版本交付。
- 后续接入通常只增加配置与驱动，但仍需真实厂商测试，不能承诺零成本适配。
- 首版仍承担可靠续传、三平台和多入口的一致性成本；简单分层不替代这些验收。
- SPEC 维护产品与质量要求，架构文档维护模块与数据流，开发规划维护阶段与版本顺序，README 只概括面向用户的范围和状态。
